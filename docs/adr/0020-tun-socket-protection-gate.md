# TUN 保护能力先于监听栈发布

状态：accepted

日期：2026-11-05

Android 建立 VPN 后，出站 socket 需要调用平台保护才能避开自身路由。原 `TunHandler` 在发布 socket hook 后启动 TUN 栈，但只在 listener 返回并赋值后才调用保护；同时忽略平台返回的 `false`。本地 Flutter 基线也有这一行为，因此这是共用核心适配层的缺口，不能归为 Kotlin 独有问题。

保护回调现在由独立 `socketProtectionGate` 持有，在 hook 发布前就绪，不依赖 listener。`RawConn.Control` 错误、平台拒绝保护和已关闭 gate 都向拨号返回错误。关闭时先撤下活动 handler，再等待已进入的保护调用结束并释放回调；已读取旧 handler 的迟到调用不能继续无保护拨号。TUN 启动仍在 handler 锁外运行，避免初始化拨号回入造成死锁；启停仍由现有串行锁和唯一运行管理器负责。

这会改变平台拒绝保护时的行为：该次拨号明确失败，不再视为成功。没有活动 TUN 时的普通代理拨号沿用原行为。Mihomo 子模块、节点选择、DNS 配置及调度、重试策略和原配置正文均不修改。

只读启动快照记录保护阶段、计数及进程内单调时间，并区分 DNS 更新提交、执行中和执行完成序号。这些独立原子字段用于观察，不构成一致事务快照或 DNS 就绪屏障。显式验收请求可按源端口开启有界诊断，在应用事件队列之前保留错误类别和端点哈希；默认关闭，不保存节点名、地址或原始错误，不承诺上游日志本身无丢失。

定向竞态测试覆盖启动前保护、拒绝及 Control 错误、关闭等待与迟到拒绝、并发计数；真机与构建结果记录在 `system-vpn-protection-redmi-20261105.json`。修复可证实的保护缺口不等于证明它导致此前的 TLS EOF，有限轮次成功也不代表长期或全部 OEM 稳定性。
