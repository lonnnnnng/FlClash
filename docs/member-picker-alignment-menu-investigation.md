## 开发中发现的差异与红绿证据

这是 Kotlin 新候选的对齐缺口，不是 Flutter 或 Mihomo 上游缺陷。

1. 新增代理错误地经过完整成员重排：原 `[A] + use:[cloud]` 新增 B 后得到 `A,cloud,B`，并产生 `use-position`；Flutter 只向对应字段追加，结果应为 `A,B,cloud`，已有显示布局也应保留。
2. 复制组只复制 JSON，遗漏显示布局，导致副本混排顺序丢失。
3. 选择页重建只保存原 JSON，没有保存原布局；父层最新布局可能混入撤回基准。编辑器比较基准也需随入场草稿冻结，不能因无关 overrides 更新而漂移。

`member-red.log` 中相同的追加/复制断言为 5 项中 2 失败；修正后成员 7 项 JVM 全过，新增原 `use-position` 保持断言后再次 7/7。覆盖分类排除、重叠筛选撤回、混排/元数据回读和未知字段保留。服务新增 1 项覆盖无关 DNS 修改及 YAML 隔离。

同步复查时比较上述 Flutter 方法及 Profile 表单保存边界，保留“各字段追加”和“显式排序才重算位置”的区别。只有等价实现通过布局复制、撤回/恢复和 YAML 隔离回归，才可替换当前补丁。

## 菜单实验：未保留产品优化

假设：正文模糊离屏目标逐帧改变尺寸，引入 RenderThread 额外执行成本。候选固定正文 `GraphicsLayer.record` 边界，并保留阴影/模糊外扩；不改动画时间或透明度。候选源码与 APK 已单独留存，最终产品 `AppMenuMorph.kt` 恢复为原实现。

新增无线程采样入口与已有线程采样入口共用三轮开关流程。每个动作约 800ms，关闭在原动画结束后、Popup 移除前留窗采帧；禁用 PNG、录屏和方法采样。按窗口统计，不与进程计数相加。

第二次原实现已接近候选，缺少稳定可归因收益，因此撤回。20 个固定时间/深浅开关截图中 11 个逐像素相同；其余 9 个最大通道差 5/255，最大平均绝对通道差约 0.0304，集中在模糊正文早段；不记为全部像素一致。

候选独立深色线程诊断得到 idle + 三轮开关共 7 组样本及 6 帧表：打开 main 506.957–549.395ms、RenderThread 485.915–501.549ms；关闭 main 252.363–294.339ms、RenderThread 205.768–213.804ms。本次读取无失败，但存在探针开销、采样间隔与线程集合边界，不能当作菜单独占耗时、GPU 时间或原生函数栈。

Perfetto 服务可查询不代表 ftrace 可用；本轮没有重复已知会使 `traced_probes` 卡 D 的采集。原生函数归因仍未完成，现有 ROM 限制见 [关闭窗口调查](menu-close-window-investigation.md)。
