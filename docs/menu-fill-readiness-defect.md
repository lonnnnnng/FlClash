# KUI-025：源按钮底色交接与玻璃开场证据

2026-11-09，接续 `1d70403a` 的菜单视觉对齐。固定参考 Flutter `be847366` / Prism `63450c0`，不合并 Flutter 提交、不改 Mihomo。

## 来源与问题

Prism `popup.dart:1442` 的 `_sourceColor` 先读取真实控件的 CardSurface/Surface 底色；没有可用底色时，玻璃采用透明，普通材质采用 `SurfaceLevel.floatingOf`。`popup.dart:909` / `:1081` 在普通开场/回源沿 sRGB 通道交接按钮底色与菜单底色；玻璃仅叠随进度退去或恢复的按钮色，不盖不透明菜单。

Kotlin 原 `appMenuMorph` 始终填充菜单底色，没有携带源控件底色。配置空态的蓝色胶囊、代理组深色按钮和菜单面板的底色不同时，交接阶段出现异色主体。源快照仍包含按钮完整外观，但不能覆盖变形主体的所有区域，因此截图存在不能替代主体底色。

另一个缺口在验收：`LiquidMenuInstrumentedTest` 以 `source.hidden` 加150ms实际等待判断玻璃准备完成。然而该标记只说明源快照交接，后台预模糊仍可能未完成；KUI-018至024的两张玻璃开场图曾只包含源按钮，已明确不计展开通过。不能增加更长固定等待就把它改成已验。

## 实现

`appMenuSource` 接收真实控件底色并随主题/入口更新，配置顶栏、空态和代理两入口接入；透明图标入口保留上游普通/玻璃默认。`AppMenuMorphFrame.fillColor` 将底色交接绑定材质进度，玻璃只叠源底色的透明度。菜单正文/源图模糊、回源时长及选择时序不改变。

测试改为观察实际platter宽度离开初始源形状，再推进受控时钟采展开帧；增加准备阶段取消及迟到结果不复活检查。条纹宿主的真实Window捕获同时检查：展开中宿主变色而菜单像素保持，重开后菜单像素随新背景改变；只验证实际捕获与冻结语义，不宣称等同Flutter实时玻璃或精确光学。
